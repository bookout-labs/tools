# Foreman glossary

| Term | Meaning |
| --- | --- |
| `foreman_repository` | The `bookout-labs/tools` repository that contains Foreman and its blueprint. |
| `target_repository` | The repository of the admitted issue and the only destination for that run's changes. |
| `target_checkout` | The pinned checkout of the target repository. Implementation owns its editable worktree. Verify runs the app there read-only and writes captures to its attempt scratch. |
| Related repository | A repository the target depends on, named in the contract file. Foreman pins it at admission to its default-branch head, records the pin on the run and checks it out read-only and adds it as a read root for the workers. Writes stay in the target repository. |
| Contract file | `.foreman/contract.yaml`, the one tracked file in a target repository that describes it to Foreman: the check command and the JUnit XML test reports it writes, container image and setup, whether the container keeps the network after setup, how to start the app and tell it is up, the related repositories, the names of the secrets the app needs, the verify skill path, the mutation command and the production check. |
| Protected file | A file a feature run never changes: the check command, CI workflows, the verify skill, accepted tests and the contract file. A change to one is its own issue with its own Foreman run, checked by the base's unchanged check. |
| Doctor | `foreman doctor --repo OWNER/NAME`, plain code that checks a target repository is ready. At every start of a run, before any paid call, the runner runs its GitHub requirements before the graph. Only a new run then runs its contract requirements, in triage.admit. Its full part runs from the command, and at admission whenever the contract file's current digest has no green full check recorded: it builds the image, runs the check, the mutation command and the production check, starts the app and related services and runs the branch probe. Each requirement that is not met is named with its exact fix. Its quick requirements come in two groups: GitHub requirements (App install and its event subscriptions, the login and budget cap variables, the login's write access, Ready label, merge queue ruleset) and contract requirements (the contract file and the verify skill at the pinned base). |
| Attempt container | The container built from the contract file's image and setup commands. Workspace owns the run's container and rebuilds it when the run has none. The worker CLIs run on the Foreman host, where their model credentials stay. Every shell command the builder, the acceptance test writer, the verifier and the reviewer run goes into it, so they can start the app and its related services. A call whose shell cannot be routed into it fails closed and runs no command on the host. It reaches the network only while Foreman runs the setup commands, unless the contract's network is run because the app uses remote test services. After setup it has loopback only. |
| Blueprint | The versioned design the human approves for future Foreman runs. |
| Run | One execution for a GitHub issue under a pinned blueprint and runtime release. |
| Start | Foreman beginning a new run or resuming a halted one. A new run begins on a Ready label event, when merge.release starts a dependent, when a prerequisite that no Foreman run owns closes, or when merge.revert files a revert issue. Resuming a halted run begins only on a Ready label event. A wake that continues an open run, an answer's included, is not a start, even where a step says it resumes. |
| Wake | What a delivery that is not a start sends to a run that has not ended, a halted one included: the human's stop or answer comment, and for a run in merge a GitHub event about its pull request or a finished check in its repository. Every wake reads for a stop before anything resumes. A wake then continues a run that waits in merge, or a run paused at a gate when it finds the answer, and resumes nothing else. A wake runs no doctor and uses the login and caps saved at the run's last start. |
| Receiver | The plain code on the Foreman host that takes each delivery from the App's webhook, verifies its signature and hands it unchanged to accept. It calls no model, and neither does accept. |
| Stage | One of seven LangGraph subgraphs. A stage owns a result and its permitted routes. |
| Step | A checkpointed node inside a stage or shared dispatch. |
| Worker | An assigned role that uses a CLI and configured model policy to perform a procedure. |
| Procedure | The prompt, skills, inputs and typed worker output for a step that calls a worker. |
| Model policy | The existing configuration for eligible models, ordering and fallback. |
| Repair turn | The one extra charged call in the same session that sends a worker its invalid answer's exact validation error. A second invalid answer stops the run. |
| Slice | One piece of work that ships as one PR. It states observable behavior: acceptance criteria, non-goals and each criterion's proof, plus declared dependencies, an advisory list of files it expects to touch and each existing test it removes or renames, with the reason. Its kind is feature, revert or protected. It never names a code edit. |
| Proof | How a criterion is proven: test, drive or contract. A test or contract proof names behavior the base lacks, so its acceptance test fails at the base. A criterion the base already meets is proven by drive. A drive criterion that cannot be driven is marked not drivable with a reason. |
| Assumption | A fact the plan relies on that lies outside the target checkout. It cites a tracked file in a related repository at its pinned commit, or it becomes a gate question. |
| Candidate | A saved plan or supplied slice bound to a repository, issue, base revision and content digest. |
| Ready label | The issue label that asks Foreman to run the issue. Adding it starts a new run or resumes a halted one. It grants no authority to merge or answer gates. It is also the first run label (intake.run_labels.ready). |
| ready (spec outcome) | The draft worker's claim that the candidate is complete enough to validate. |
| Ready repository | A target repository that passes doctor's check. One that does not stops a start with not_ready. |
| Approval | An authorized person's explicit assent for the named choice. The coordinator or personal agent posts it as an issue comment under the human's identity. A plan and a merge need none. |
| Human's identity | The GitHub login saved on the run, read from the `FOREMAN_HUMAN_LOGIN` repository variable at the run's last start. Only issue comments under that login count as the human's answers, cancellations and stops. |
| Stop | An issue comment under the human's identity whose first line is `foreman stop`, created after Ready was last added to the issue. Each stage's first step reads the issue for one before any paid call or write and ends the run cancelled. At a start, doctor's GitHub requirements come first. A stop also wakes the run, whatever it is doing, and every wake reads for a stop first. So a run that is waiting, paused at a gate or halted ends cancelled before any paid call or write, and a stop posted while a run is running is handled as soon as the run stops running, unless the run has ended by then. In merge, a stop after the pull request merged is too late. |
| Gate | A saved pause for the human's answer to a specific unresolved choice. The coordinator or personal agent posts the answer or cancellation as an issue comment under the human's identity. The App's issue comment webhook delivers the answer to the paused run. Adding Ready does not. |
| Reply marker | The line `foreman answer` followed by the question's digest, which Foreman gives in each gate's question. An answer is an issue comment under the human's identity whose first line is exactly that line, with the answer, or `cancel`, on the lines after it. |
| Settled ruling | A saved human answer that later checks of the same issue get as context and cite by ID. |
| Halt | A named stop with evidence. The run keeps its checkpoint, and adding Ready resumes it at the halted step, or at the step the stage's recovery names for that halt. not_ready is the exception. At admission not_ready starts no run and keeps nothing. From the runner it is not a halt: a new run keeps nothing, and a resumed run keeps its earlier halt. A GitHub read that fails in the runner is reported as git_failed the same way and is not a saved halt either. A wait in merge for GitHub is not a halt and keeps the run open. Foreman has no other wait. A stop ends a halted run cancelled, unless the run is in merge and its pull request has merged. |
| Status comment | The one status comment Foreman keeps on an issue, found by Foreman's status marker. It shows the latest run's state, its typed result and links, and its run report. Every write is a whole rewrite from the checkpoint. Admit's not_ready, a halt before admission and the runner's not_ready or git_failed report at a start are shown with no run report. A failed rewrite changes nothing in the run. |
| Run report | The record of a run that its status comment holds: the repository and issue, the stage and step it is in or stopped at, the steps taken, each worker call with its model, its skills by ref, its outcome, tokens and dollars, the spend against the caps, the rounds used, the blueprint version, the skill pins, each escape by its kind with a link, and each scorer's spend. It is the same on every machine, because it is on GitHub. It holds no text a CLI, a provider, a worker or a person wrote, no host path and, beyond the skills, no file a worker read. |
| not_ready | The stop when doctor's check finds a requirement not met at a start. GitHub refusing the App's read is a requirement not met. A failed read is not not_ready. It names the missing requirement and its fix. A new run does not start, and a resumed run keeps its place. Foreman reports it in the issue's status comment. |
| git_failed | A Git or GitHub operation failed. In a stage or in dispatch it is a saved halt. In the runner it is a report in the issue's status comment that saves no halt: at a start, when a read of doctor's GitHub requirements fails, and on a wake, when a read the runner makes before the run continues fails. The first starts nothing and the second continues nothing. |
| Failed read | A read of doctor's GitHub requirements at a start that gets no answer, a server error, a rate-limit answer, or any other answer, unless that answer is the read's result, shows that a requirement is missing, or is a refusal of the App. The runner reports it as git_failed. It is never not_ready. On a wake, a read the runner makes before the run continues (of the issue for a stop or for an answer, or of the pull request for a run paused at merge's gate or halted in merge) is a failed read whenever it does not get its result, whatever GitHub answered, because no doctor runs on a wake. The runner reports that as git_failed too. |
| Checkpoint | LangGraph's saved continuation and input records for this run. |
| Paid call | One worker CLI call that spends model tokens. Dispatch reserves and charges each one. |
| Budget cap | The most a run may spend, in dollars (FOREMAN_MAX_BUDGET_USD) and in tokens (FOREMAN_MAX_TOKENS). A run that reaches one stops budget_exceeded, and resumes when the operator raises the cap and adds Ready again. Unset, they are 3 dollars and 20,000,000 tokens. The run uses the caps saved at its last start. |
| worker_unavailable | The halt when every qualified model for a call is out of quota or has no installed CLI. Foreman does not wait for capacity. When Ready is added again the run makes that call again as a new attempt. |
| Reservation | A durable record of authorized spending and identity persisted before a paid worker call. |
| Attempt | One worker execution identified by its reservation and recorded response or usage. |
| Attempt scratch | The directory on the Foreman host where one worker call writes its temporary files and captures. Foreman makes one for each call inside the scratch root, which is Foreman's state directory. The attempt container mounts it at the same path, as it mounts the checkout. It is never inside the target checkout and never in the system temp directory that the host's other processes share. A verifier's outlives its call, so the captures its evidence names stay readable. Review's demonstrate step gets one for the demonstrations it runs. |
| State directory | The directory on the Foreman host that holds the run's checkpoint database. By default it is `$XDG_STATE_HOME/foreman`, or `~/.local/state/foreman` when that variable is unset. The checkouts Foreman manages sit inside it. |
| Base revision | The Git commit that pins the starting target checkout. A review also records its PR diff base. Also called the pinned base. |
| Candidate's base | The commit a candidate's tree and test report are compared with, so the builder cannot weaken the checks. It is the pinned base, or after a base merge the last base head Foreman merged, which the run saves with its report. The pinned base itself never changes. |
| Head | The exact commit on the PR's source branch at the moment of observation. |
| Acceptance tests | Tests and fixtures a separate worker in the verifier role writes from the plan and the base tree before the build. Plain code proves the check collects them and that they fail at the base. The builder cannot edit them. |
| Test ID | The case's file made relative to the checkout root, empty when the report names none, its enclosing suite names, its classname and its name, read from the contract's JUnit XML test reports. Cases that share an ID are one test with a count: it passed only if every case passed, and a lower count than the base's is a missing test. |
| Checked tree | The exact tree whose unchanged contents passed the contract's check command, including the accepted tests. |
| Mutation check | After a passing check, plain code flips a capped sample of changed lines with the contract's pinned tool and reruns the tests. A mutation no test notices goes back to the builder as a finding. The builder adds a test that notices it or names it an equivalent mutation, with the reason no test can, and the next sample leaves it out. Review rules on each claim, and a rejected claim is a blocking finding. |
| Receipt | Saved evidence of one observed GitHub, Git or worker result. |
| Arm | Ask GitHub to queue or auto-merge the exact reviewed commit when eligible. |
| Production confirmation | The contract's read-only production check, run by Foreman against the merge commit after a merge. A failure files a revert issue and a regression issue. |
| P0 / P1 | Typed priorities for critical or serious evidenced correctness, security or scope defects, or a fix-or-patch finding that cites the code it duplicates or works around. |
| Demonstration | A test or command attached to a blocking review finding that Foreman runs at the reviewed head. A finding whose demonstration does not fail is advisory. |
| Advisory | A finding that can be posted without requesting implementation again. |
| Waiver | An exact, temporary structural difference with a migration issue and a condition for removal. |
| Scorer | A versioned rubric that assesses recorded work without deciding workflow routes. |
| Hand fix | A person modifies the change or repairs a run to get the PR to merge. A commit on the PR's branch that the App did not make is recorded as one. After the merge, the human records one with an issue comment whose first line is `foreman escape`. |
| Escape | A defect that got past Foreman: a hand fix, a revert or a failed production check. Foreman records each one on the run. It is closed by a change to the target repository's tests, verify skill or conventions, or to a prompt, never by a new guard in Foreman. |
| Criterion | One acceptance criterion of a slice. Verify reports each one as passed, failed or unverified. |
| Evidence | What the verifier did and observed for each criterion at the tested head, and where its captures are saved. Foreman posts it as one comment for that head, marked stale if the head moved. |
| Item N | Item N of the owner's 2026-11-24 redesign brief in [tools #299](https://github.com/bookout-labs/tools/issues/299). Blueprint v3 names the item behind each rule it changed. |
| merge B | The owner's ruling 57aa3a15: Foreman merges even when the reviewer is the builder's model family, and no change adds a human approval or merge step (D13). |
| verify A | The owner's ruling 67c6553f: a failed Verify criterion goes back to Implement, and an unverified drivable criterion blocks the merge (D11). |
| rollback A | The owner's ruling 74a43493: a failed production check reverts Foreman's own merge through a Ready revert issue (D12). |
| Revert run | The run of a Ready revert issue that merge.revert files. Its slice has kind revert, which only merge.revert sets, and carries the merge commit SHA it undoes. Admission accepts a revert slice only on the issue the App filed for a revert recorded on a Foreman run. It is not a feature run: it skips acceptance tests and the mutation sample, and it may delete exactly the tests the reverted merge commit added. |
| CARR record layer | The owner's team record and doctrine store. It supplies authorized team context to the coordinator or personal agent. Foreman never reads it. |
| T3 Code | The desktop app that hosts the coordinator or personal agent and its conversation context. Foreman never reads it. |

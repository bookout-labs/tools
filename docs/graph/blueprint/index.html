Where Foreman works

The human works through a coordinator or personal agent. The agent files the GitHub issue and posts the human's answers, comments and stop requests as issue comments under the human's identity.

Foreman runs from bookout-labs/tools. Each issue names the repository where its changes belong. The issue's run label and status comment mirror the run state and show the result. GitHub, the CARR record layer (the team's record and doctrine store) and T3 Code (the app that hosts the coordinator or personal agent) hold shared context. Git versions the blueprint.

What a target repository supplies

One tracked file in target_repository holds everything that describes the repository to Foreman (item 22). It is versioned with the code it checks. It replaces the FOREMAN_CHECK variable, tools #292's .foreman/environment.yaml and the requirements that today are spread over the App install notes, cli.py, github.py, skill_rules.py and README.md.

Contract file .foreman/contract.yaml

  • check: a string. The repository check command. Foreman runs it in the attempt container and requires exit 0 on an unchanged tree. Each run of it that Foreman makes, at prepare, at edit and in doctor's full check, is allowed check_timeout_seconds. A run that has not ended by then is ended and did not pass.
  • check_timeout_seconds: a whole number of seconds, one or more. The time each run of the check command is allowed. A contract that does not set it gets 1800.
  • test_report: one relative path, or a list of them, inside the checkout, that the check command writes as JUnit XML. The files are generated and need not be tracked. The repository git-ignores them, so the check leaves the tree unchanged and they never enter the checked tree. An absolute path or one that leaves the checkout is rejected. Foreman removes them before each check run and reads only what that run wrote. Foreman reads each test case's ID and result from them without knowing the language. A test ID is the case's file made relative to the checkout root, empty when the report names none, its enclosing suite names, its classname and its name. Cases that share an ID are one test with a count: it passed only if every case passed, and a lower count than the base's is a missing test. The accepted tests are the IDs the base check run with the acceptance tests reports beyond the base's report. implement.tests uses them to prove the accepted tests are collected and fail at the base, and edit compares the test IDs in the reports at the base and the candidate to find a deleted or added skip (items 9 and 10).
  • image: a string. The image of the attempt container, where every shell command of the builder, the acceptance test writer, the verifier and the reviewer runs (item 3).
  • setup: a list of strings. Setup commands that run in order in a fresh attempt container before any worker starts. Foreman allows thirty minutes for a container to be ready, from the start of the image pull to the end of the last setup command. A container that is not ready by then did not build.
  • network: setup or run. setup is the default: the container reaches the network only during setup. run keeps it connected, for a repository whose app uses remote test services, such as a hosted test database or sign-in provider, or whose changes add or update dependencies. With setup, nothing in the container can fetch a package after setup, so a change that needs a dependency the base does not already install cannot be built or checked there.
  • start: a map with command, the command that starts the app, health, a command that exits 0 once the app is up, and timeout_seconds, how long to wait for health. Optional: a repository with no app leaves start out, and doctor skips the start requirement.
  • related_repositories: a list of maps, each with repository as OWNER/NAME, start as the command that starts its service in the attempt container, health as a command that exits 0 once the service is up, and timeout_seconds, how long to wait for health (item 4). The contract pins no commit. Admission pins each one for the run.
  • secrets: a list of names, each a valid environment variable name ([A-Z][A-Z0-9_]*). The secrets the app needs to start. Foreman supplies each one's test value from the Foreman host's environment variable FOREMAN_TEST_<NAME> as a variable of that name in the attempt container. Production credentials are never used. Foreman's redaction also removes each test value the run supplied from every text it writes to GitHub and to its run log.
  • verify_skill: a relative path under rules.paths that names a tracked regular file at the base. The repository's verify skill. The skill says how to start the app, how to sign in with a test account and what counts as evidence.
  • mutation: a map with command, the pinned mutation tool command, and sample_cap, the most changed lines the mutation check flips (item 15). Foreman gives the command the sampled changed lines as a file:line list on standard input, one per line. The command prints one JSON line for each mutation it made, with its file:line, an id the tool keeps the same across runs, and killed or survived. equivalent_mutations names a mutation by that id. Foreman stays language-neutral.
  • production_check: a map with command, a read-only command that confirms a merge commit in production, not_deployed_exit, an integer from 1 to 255, the exit code that means the commit is not deployed yet, and timeout_seconds, the time limit for production confirmation (item 20). Foreman runs the command once, with the merge commit SHA as its argument and no credentials in its environment. The command itself waits for the deploy, within timeout_seconds. The command reads the deployed commit from a source that needs none, such as a public version endpoint the app serves or the commit its deploy reports publicly. It exits 0 when production runs the merge commit and the check passes, not_deployed_exit when production still runs another commit once it stops waiting, and any other code when the check failed. A repository with no deployment names a check of its default branch at the merge commit.

A contract field without a default becomes required in the build slice that first uses it. Until that slice ships, the contract parses and doctor passes without it. A field with a default, such as network or check_timeout_seconds, stays optional.

Repository variables keep only what the operator controls: FOREMAN_HUMAN_LOGIN, the GitHub login whose issue comments count as the human's, the budget caps FOREMAN_MAX_BUDGET_USD and FOREMAN_MAX_TOKENS, and FOREMAN_MERGE_HOLD. An unset FOREMAN_MAX_BUDGET_USD is 3 dollars (the owner's 2026-11-23 ruling, tools #26 comment 7111974499) and an unset FOREMAN_MAX_TOKENS is 20,000,000 tokens. Doctor requires that the FOREMAN_HUMAN_LOGIN account can write to the repository: the permission field of GitHub's repository permission for that login is admin or write. GitHub reports the maintain role there as write and the triage role as read. Only that login's comments answer, cancel or stop a run. So a login that cannot already change the repository's code never gets that say, and a misspelled login stops the start instead of beginning a run nobody can answer.

Quick part

The command runs all of it. At every start of a run the runner (src/foreman/runner.py) runs the GitHub requirements before it enters the graph, so that check has no step or transition. Only a new run then runs the contract requirements, in triage.admit, after the stop read, the issue checks and the pin. The quick part reads GitHub and the contract file and starts no container.

GitHub requirements

  • the GitHub App is installed on the repository, GitHub lets it make doctor's reads, and its installation is subscribed to the events that start and wake a run: issues, issue_comment, pull_request, pull_request_review, check_suite and status
  • FOREMAN_HUMAN_LOGIN is set and not blank, and each budget cap that is set parses. An unset cap uses its default.
  • the FOREMAN_HUMAN_LOGIN account can write to the repository
  • the Ready label exists
  • a merge queue ruleset protects the base branch

Contract requirements

  • the contract file parses strictly, so an unknown or duplicate key is named, and validates
  • the verify skill exists at the contract's path

Full part

Run by the command after the quick part, and by triage.admit after the quick part whenever no green full check is recorded for the contract file's digest at the base, so a change to the contract file is checked once at the next admission. Each green full check is recorded in Foreman's state directory on its host, keyed by repository and contract file digest. A failed full check stops admission with not_ready.

  • the contract image builds
  • the setup commands succeed within the thirty minutes a container is allowed
  • the check passes on the default branch within the check_timeout_seconds of the contract it checks
  • writes its test report and leaves the tree unchanged
  • the mutation command runs on the default branch
  • the production check command runs against the default branch head
  • the app starts and its health command answers, when the contract names a start
  • each related repository checks out at its default-branch head, its service starts and its health command answers

Each requirement that is not met prints the one missing requirement and its exact fix. At a start it stops with not_ready, and no run starts or resumes. Doctor reports not_ready only when GitHub answers and the answer shows a requirement is missing. GitHub refusing the App's read is such an answer. A failed read, the permission read included, is never not_ready, so an outage never tells the operator to change a setting. The fix for the App's event subscriptions names each missing event and the App permission that event needs. The fix for a check that does not end within its time limit names that limit and says to make the check faster or raise check_timeout_seconds.

docs/target-repo-setup.md lists each requirement, why Foreman needs it and how to supply it (item 24). It is generated from doctor's requirement list and a test fails if the two differ. App and engine are set up by ordinary PRs in those repositories with a green doctor as their acceptance test. No onboarding command is built until a third repository needs one.

How runs are scored

Scorers read recorded work and never decide routes (item 21). Each scored run stores its label and reason with the run. Foreman records each escape on the run. An escape is closed by a change to the target repository's tests, verify skill or conventions, or to a Foreman prompt. It is never closed by a new guard in Foreman. The coordinator or personal agent finds that change with pstack correct, outside the stages (D7). No Foreman worker loads it.

After a run records its terminal result, Foreman scores it once with each scorer that has work to judge. When an escape is later recorded on the run, Foreman scores its review again. Scoring runs outside the stages and never changes the run's result. Scorers call workers through worker, not dispatch, so their spend stays outside the run's budget ledger, and the run report lists it.

Foreman records a revert and a failed production check itself. A hand fix reaches the run two ways. A commit on the PR's branch that the App did not make is recorded as a hand fix when Foreman next reads the PR. After the merge, an issue comment under the human's identity whose first line is foreman escape records one, with the comment as its evidence. The App's issue comment webhook delivers it to the issue's latest run.

Each score is a fresh session on the next available qualified model in the configured review order, preferring a family that did not do the work it judges. A scorer that finds no available model leaves the score unknown.

Task compliance

Judges implement. Did the merged PR deliver what the issue asked for, and only that? Judge scope from the issue text, not from the PR's description of itself.

Labels: compliant, partial, non_compliant

Review quality

Judges review. Did each blocking finding carry a failing demonstration or a cited file:line, and did the review miss a defect that later escaped? A review with no blocking finding and no later escape is clean.

Labels: actionable, vague, empty_or_noise, clean

Warp equivalent

Worker invocation and conversation reuse

Local CLIs need crash recovery and token and dollar accounting at one shared boundary. Warp continues a worker's conversation for follow-ups and revisions. Foreman saves the builder's session on every accepted answer that reported its totals and resumes it when the checkout fingerprint matches. Warp's stage outputs are instructions, not typed schemas, so Foreman adds one repair turn for an answer that fails output validation.

Scope, recovery and checks
  • Runner acquires a per-repository and issue OS lock before loading the LangGraph checkpoint. Release on pause or process exit.
  • Save run, worker procedure, candidate or head, attempt id, allowance and worktree identity before every paid call.
  • Resolve worker model and CLI configuration independently of the stage procedure. At admission, FOREMAN_MODELS can supply one ordered list for all worker assignments. When unset, use the per-node orders in models.toml. The checkpoint's run state saves the ordered model names by node in model_orders. Every resume and wake uses those saved orders. The procedure owns instructions and typed outputs.
  • Resume at the interrupted step and reconcile before any repeat. A call is sent once dispatch has saved that it is starting the CLI, and it saves that before the CLI starts. A reservation with no such record was never sent: it is charged nothing, and the call is made under that same reservation, as the same attempt. Charge each attempt once. Usage is ambiguous when a call was sent and a figure that dispatch counts did not come back, because the call left no result or because its answer did not report it. Each figure is judged by itself: one that was reported is charged as reported, and one that is missing is charged the worst case, with usage unknown logged. Where a CLI reports a conversation's running total, a resumed call is charged that total less the total the conversation reported at the answer it resumed, taken model by model as the CLI reports them. A model the earlier answer did not report subtracts nothing. A figure that cannot be found that way is missing, as when the earlier answer reported a model the later one lacks or a total is lower than it was. The worst case is the allowance saved on the call's reservation: the whole token remainder, and for a call whose dollars dispatch counts the whole dollar remainder. It is the most the call was allowed, and any smaller figure is a guess. It is not a proof of what the call spent, because the one response that crosses a dollar cap still finishes and is billed (DP8). Under the caps the reservation was made with, nothing remains after that charge, so the run stops with budget_exceeded and makes no call. An answer whose charge reaches a cap, by a reported figure or a missing one, is not adopted: the step stops, as in DP8, and the call is made again when the run resumes. A start that read a higher cap has the difference left, and the call is made within it. A call that was sent and left no result, because its process died before one was saved, is a cut-off call. When it was a builder's, the edits it left in the checkout are that attempt's own. The tree then differs from the worktree identity saved on the reservation, and that difference is taken as the cut-off call's work. When the checkout is still on the owned branch at the attempt's parent, the call made again continues on those edits. Otherwise the run stops dirty_worktree and preserves the tree. Foreman has no fingerprint of the edited tree, because the cut-off call saved none, so the branch and the parent are all it asks. The call made again starts a fresh session whether or not the cut-off call left edits: when dispatch charges a builder's cut-off call it drops the builder's saved session, because that session may hold part of the cut-off call. Where the reservation was never sent, no worker of this run wrote after it was saved, so a checkout that differs from the identity saved on it holds edits that are not the run's, and the run stops dirty_worktree. The status comment says that the call's spend is unknown and was charged in full, names each cap that the charge reached by its variable, FOREMAN_MAX_TOKENS or FOREMAN_MAX_BUDGET_USD, and says that Ready makes the call again once each is raised.
  • An answer that fails output validation, its schema or the stage's own checks of it (dispatch.py:208, delivery.py:141), gets one repair turn (item 1). Dispatch reserves a charged call that resumes the same session with the exact validation error. A second invalid answer to the call stops with invalid_output, whichever model gave it. The repair turn is made only in the session that gave the invalid answer. When quota ends it, it is not made again and its session is not kept: the next qualified model gets the original call in a fresh session. A repair turn that was sent and left no result is not made again either, because the session it was sent into may hold part of it: the call is made again from its original instructions in a fresh session, with its own repair turn. When no model is available the run stops worker_unavailable, and the call that Ready makes again is a new call from its original instructions, with its own repair turn.
  • Only the builder keeps a conversation (D5, item 2). For implement.edit, save the native session in run state on every accepted answer as well as on quota. A session is saved only together with the totals its CLI reported for it. An answer that reported none leaves no saved session, and the next call starts fresh. A later implement.edit call for the same PR resumes it only when the checkout fingerprint matches the saved one. Otherwise it starts fresh. Every other procedure starts a fresh session for each call, the call that Ready makes again after worker_unavailable included. The one exception is a repair turn, which stays in the session of the answer it repairs.
  • The allowance is the caps saved on the run at its last start, minus what the run has spent. Dispatch reads no repository variable.
  • Admit a call whenever the remaining dollar allowance is positive. Dispatch counts dollars only for a CLI that reports what each call cost and takes a spending cap, which today is the Claude CLI alone, and it passes that CLI the remainder as its spending cap. A call through any other CLI spends no counted dollars and is bounded by the token cap. Foreman never guesses a minimum cost for a call. A CLI checks its cap only after a response arrives, so the one response that crosses the cap still finishes and is billed. Dispatch charges the actual spend and then stops with budget_exceeded.
  • budget_exceeded is resumable (item 19). After the operator raises the cap and adds Ready to the issue again, the run resumes at the interrupted step within the new allowance.
  • Try available qualified models within the token and dollar allowance. Review prefers another model family and falls back in configured order once that preference cannot be met. A quota or missing CLI moves to the next qualified model. When none is available, dispatch stops with worker_unavailable. Each attempt that ended on quota or a missing CLI is recorded with that outcome before the halt, so the halted run holds no reservation without a result. Foreman has no wait for worker capacity and schedules no wake. The status comment names each model tried and what its CLI answered, and says that Ready makes the interrupted call again once a provider has capacity. After Ready is added again the run resumes at the interrupted step. Dispatch makes the call as a new attempt with its own reservation and charge, and chooses among the qualified models from the start of their order, as for any call. The call that Ready makes again resumes a saved session only when it is a builder call, the chosen model is the one that holds that session and the checkout fingerprint matches. Retain the caller's continuation and recheck branch, parent and fingerprint before continuing partial edits.
  • A model whose CLI cannot route its shell into the attempt container is not qualified for implement.tests, implement.edit or verify.drive. Dispatch moves to the next qualified model, as it does for a missing CLI. A reviewer without the route still qualifies; its shell commands, the check included, fail closed.
  • Every worker call writes its temporary files and captures to its own attempt scratch, a directory Foreman makes for the call inside the scratch root. The scratch root is Foreman's state directory on its host. The attempt container mounts the attempt scratch at the same path, as it mounts the checkout, so a worker's shell commands and its CLI's file tools write to the same place. A worker whose scratch root, with symlinks resolved, is its target checkout or a directory inside it is refused. This is a setup error on the Foreman host, not a halt and not not_ready. The foreman command exits non-zero before any worker call, naming the scratch root and the checkout, and changes nothing on the run or the issue. A worker cannot be built without a scratch root, so Foreman has no fallback location and never moves the scratch elsewhere. No worker call writes to the system temp directory that the host's other processes share. Foreman's own short-lived files, such as the skills export and doctor's clone, and files a command writes inside the container's own filesystem are outside this rule.

Cases the implementation must pass

  • The charged result is replayed

    One ledger row and accepted response.

  • Crash before the call is sent, after it is sent with no result, or after a durable result. On another call the answer reports no usage

    Reconcile at the interrupted step before repeating. A call that was never sent is made under its saved reservation and charged as any call. A finished result is adopted. A call that was sent and left no result is logged usage unknown and charged once, with the allowance saved on its reservation. Under unchanged caps the run then stops budget_exceeded with no call, and after the operator raises each cap that was reached and adds Ready, the step makes the call again. The answer with no usage is charged the same way and is not adopted. The run stops budget_exceeded, and after the caps are raised and Ready is added the call is made again.

  • Every qualified model runs out of quota after partial edits, and Ready is added once one is available again. On a second run the same happens during verify.drive. On a third run a builder's repair turn ends on quota, every other model is out too, and Ready is added

    The run stops worker_unavailable under the Stopped label, and the status comment names the models tried and says Ready makes the call again. The start resumes the interrupted call with the verified caller and fingerprint under the remaining allowance, as a new attempt with its own charge. The builder's call resumes its saved conversation when the chosen model is the one that holds it and the checkout fingerprint matches, and starts a fresh session when another model is chosen. The attempts that ended on quota are not charged again. Ready added while every model is still out stops the same way and charges nothing. On the second run the verifier's call starts a fresh session. On the third run the call is made again from its original instructions, the validation error is sent to no session, and an invalid answer to that call gets its own repair turn.

  • Two wakes for one issue checkpoint

    At most one active writer, no duplicate charge or external write.

  • A scripted worker returns one invalid answer then a valid one. On a second call the repair turn ends on quota and the next qualified model answers

    The stage finishes with one extra charged call in the same session. Two invalid answers stop with invalid_output. On the second call the next model gets the original call in a fresh session and is not sent the validation error. A valid answer from it finishes the stage, and an invalid one stops with invalid_output.

  • An accepted builder answer then a failed check at a matching fingerprint. On a second call a scripted worker returns an invalid answer and then a valid one. On a third run the resumed builder's answer reports a total lower than the one saved with its session. On a fourth run an accepted builder answer reported no totals, and a check then fails

    The repair call carries the saved session's resume flag and is charged its own spend, not the conversation's running total. A changed fingerprint starts fresh. The repair turn on the second call is charged its own spend the same way. On the third run that figure is missing, so it is logged usage unknown and charged the worst case, the answer is not adopted and the run stops budget_exceeded. On the fourth run no session was saved, and the repair call starts a fresh session and subtracts nothing.

  • A run stopped with budget_exceeded and the operator raises the cap and adds Ready again

    The run resumes at the interrupted step without a duplicate charge.

  • $0.25 of allowance remains and the next response costs $2.94

    Dispatch admits the call with a $0.25 CLI cap, charges the actual $2.94 once, and stops with budget_exceeded before any further call.

  • A worker whose scratch root is its checkout, one whose scratch root is a directory inside its checkout, one built with no scratch root, and one whose scratch root is beside its checkout

    The first two are refused before any process starts, and the message names the scratch root and the checkout. The third cannot be built. The fourth runs with TMPDIR inside its scratch root and leaves the checkout unchanged.

  • Scripted runs that together call every procedure's worker, each started from repository variables

    Each worker's input holds the inputs its procedure names and nothing else from the run. The login, the caps, the ID of the builder's saved session and the record dispatch keeps of each paid call are in none of them. The builder's session is resumed by dispatch, not passed as input.

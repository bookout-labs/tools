## D1. What sends a pull request back?

Agreed by the owner 2026-11-22. Only a concrete P0 or P1 correctness, security or scope defect in the full current pull request sends it back. All other findings are comments. Revised by the 2026-11-24 brief (#299, item 17): review asks three fixed questions, each in a fresh pass. A blocking finding about issue fit or breakage carries a failing demonstration that Foreman runs at the head. If it does not fail, the finding is advisory. A blocking fix-or-patch finding cites the file:line of the code it duplicates or works around. Another model family is a preference. If that family is unavailable, dispatch uses the next qualified model in models.toml order, including the builder's family. When no qualified model is available, dispatch stops with worker_unavailable, and adding Ready resumes the run (#379). Warp workers advise and can suggest revisions. [Warp code review](https://docs.warp.dev/factories/use-cases/code-review/)

## D6. How does a run start and show its state?

Agreed by the owner 2026-11-22: A. A run starts when the Ready label is added to an issue in any repository where the App is installed, on an organization or a personal account. The issue shows the run's state as one run label (Ready, Doing, Needs answer, Stopped or Done) plus a status comment with the typed result and its links, so a halt stays distinct from a merge. Project boards are optional views. An organization board can collect labeled issues with GitHub's built-in auto-add workflow. GitHub sends `projects_v2_item` events only for organization-owned Projects, so a board column cannot be the trigger for personal repositories. Warp starts runs from filtered GitHub events, including issue labels. Revised by the 2026-11-24 brief (#299, item 5): every skill loads whole at its pinned commit, as Warp loads a SKILL.md. No skill is cut to a line range. Add six methods:

- Research on bugs and regressions builds a feedback loop first with Matt Pocock's `diagnosing-bugs`.
- Spec applies the vertical-slice and blocking-edge rules from Matt Pocock's `to-tickets` when a parent splits into children.
- Verify drives the change with the target repository's own `verify-<app>` skill (D11). pstack `create-verification-skill` creates it and `maintain-verification-skill` keeps it current.
- Implement runs the target repository's own formal verification skill, `formal-<area>`, on changes that touch the verified code. pstack `create-formal-verification-skill` creates it and `maintain-formal-verification-skill` updates it when a change is intended. Formal verification is opt-in per repository: it runs only where the repository has its own skill. Agreed by the owner 2026-11-23 ("A").
- Review checks what the change could break beyond the diff with pstack `blast-radius`.
- Fix PRs driven by observed failures, outside the stages, use pstack `correct`.

Leave out `to-spec` and Matt Pocock's `triage` and `code-review`. `triage` decides with a maintainer whether an issue is ready for an agent. That work ends when Ready is added, so it belongs to the coordinator or personal agent before a run. `to-spec` writes a spec from a conversation with a person and lists the modules to build, which a slice never names (item 6). What both ask of a plan, stated behavior, testable criteria and what is out of scope, the slice schema and spec's validate step already require. Measure the selection using the synthetic benchmarks. ## D11. Where does end-to-end verification run?

Agreed by the owner 2026-11-23: "2. Warp does it that way for a reason. It's the better design choice", then "1-A, 2-yes, 3-yes". Warp runs user-level verification as its own stage with its own worker. The worker builds and starts the app from the pull request, uses it as a user would, and reports each criterion as passed, failed or unverified with evidence. It never edits, approves or merges, and the evidence complements code review rather than replacing it.

- A Verify stage runs between Implement and Review. It drives the published head with the target repository's own `verify-<app>` skill, found at the contract file's verify skill path. Doctor's readiness check requires that skill, so the `no_skill` route is removed.
- Foreman posts one evidence comment for the tested head. If the head moved, Foreman posts the evidence marked stale and returns to Implement, which reconciles the moved head as it does after Review. Warp's publication step ends instead. Foreman diverges because nothing may verify or review a head until Foreman has reconciled it.
- A known checked head that Merge returns for fresh review keeps the evidence already posted for it. Its code is unchanged, so Verify doesn't run again.
- The verifier prefers a qualified model from a different family from the builders, as the reviewer does.
- Revised by the owner 2026-11-24, verify A (decision 67c6553f): a failed criterion goes back to Implement and counts toward the failed-check cap. An unverified criterion blocks the merge unless the plan marked it not drivable with a reason. This reverses the earlier line "a failed criterion never routes straight to Implement".
- `verify-<app>` moves from Implement to the Verify worker, so the builder runs only the repository checks.
- The worker that reviews is called `reviewer`, and the new worker is called `verifier`, matching Warp's terms.

Warp's recipe starts on a maintainer's label. Foreman runs unattended, so Verify runs on every published head and gates Review. [Warp Computer Use verification](https://docs.warp.dev/factories/use-cases/computer-use-verification/)

## D12. What happens when a merge fails in production?

Agreed by the owner 2026-11-24, rollback A (decision 74a43493). After Foreman's merge, Foreman runs the target contract's read-only production check against the merge commit. If it fails, Foreman files a revert issue carrying Ready whose slice reverts the merge commit, so the revert runs through the normal path, and files a regression issue with the evidence. The run ends `reverted` and releases no dependents. This supersedes only the "a person decides on rollback" part of the 2026-11-23 ruling (tools #26). Warp's incident recipe investigates production read-only and leaves rollback to people. Foreman reverts its own merge because no person stands between review and production. [Warp production incidents](https://docs.warp.dev/factories/use-cases/production-incident-resolution/)

Warp's reviewer runs on a different model, and a human merges. [Warp code review](https://docs.warp.dev/factories/use-cases/code-review/)

## D14. What must a target repository supply?

From the owner's 2026-11-24 update to the brief (#299, items 22 to 24). Each target repository carries one contract file, `.foreman/contract.yaml`, holding the check command, its time limit and its JUnit XML test report, container image and setup commands, how to start the app and tell it is up, the related repositories, each pinned per run at admission, the names of the secrets the app needs, the verify skill path, the mutation command and the production check. Repository variables keep only the human login, the budget caps and the merge hold. `foreman doctor --repo OWNER/NAME` checks readiness in plain code. At every start of a run the runner runs doctor's GitHub requirements, and only a new run then runs its contract requirements, in triage.admit, all before any paid call. Doctor also requires that the human login can write to the repository (#357), so a mistyped login stops the start. A repository that fails any of doctor's requirements starts or resumes no run. `docs/target-repo-setup.md` is generated from doctor's list. Two choices are the auditor's, not audit findings, and stay open to pushback: moving the check command from a repository variable into the contract file, and not building an onboarding command until a third repository needs one. Warp keeps the image, setup commands, repositories and secrets in the factory definition. Ruled by Fable on 2026-11-27 (#318): the check's time limit is the contract's check_timeout_seconds, 1800 seconds when unset, because the time a check takes belongs to the repository's code and the contract is a protected file the builder cannot change. Setup's thirty minutes is one figure in Foreman, not a field. [Warp runners](https://docs.warp.dev/factories/runners/)

## D15. What did the owner rule on the v3 review's questions?

Agreed by the owner 2026-11-27: "I'll go with all your recommendations on those 18 questions". The whole-design review of the v3 build ended with 18 questions for the owner, each with options and a recommendation. Each ruling below is that recommendation. Question 2, the 15 redraws made after v3 was approved, is D17.

- Question 1, the branch probe. GitHub has no rule that refuses a push to a PR's branch only while its merge is armed, so no repository could pass the old probe. The probe now proves what GitHub does and Foreman already handles: a push while armed drops the PR from the merge queue and Foreman reads the moved head. This revises D2's 2026-11-24 wording. The probe also opens its PR again while GitHub answers that the branch it has just created is not readable yet.
- Question 3, small issues and the assumptions check. Triage only classifies, and every plan is drafted in spec.draft, so the assumptions check (item 7) runs for a small issue as it does for a large one. Triage's answer has no slice. A drafted plan with one slice is built by the same run, and a child issue carries its parent plan's assumptions, which validate checks on the child's run. The cost is one more paid call for each small issue.
- Question 4, what makes production confirm wait. The repository's production check command waits for the deploy itself, within its time limit, and Foreman runs it once. This is what was built. A GitHub deployment event that wakes confirm may come later, if app and engine report deployments to GitHub.
- Question 5, a repository with no app. The contract's start is optional, and doctor skips the start requirement when the contract names none.
- Question 6, routing defects. The gate and the record for a valid result with no route are deleted from the drawing. CI already checks that every result has exactly one route, and nothing built them.
- Question 7, the review scorer's label for a good clean review. review_quality gains the label clean, for a review with no blocking finding and no later escape, so a correct review with nothing to block is no longer scored empty_or_noise.
- Question 8, where verify's evidence goes and what the final comment links. The evidence comment stays on the PR, and the issue's final status comment links it. The run saves the link, so SCHEMA_VERSION is 43.
- Question 9, related services have no health check. A related repository in the contract gains health and timeout_seconds, as the app's start has, and its service must answer its health command before any check or worker uses it.
- Question 10, two fields with no drawn meaning. The drawing now gives the values the code uses: work_kind is feature, bug_fix, refactoring or perf_issue, and spec_gate is ready or needs_human. No code changed.
- Question 11, saved proof records. Foreman saves the mutation sample's mutations with each result, and the production check's command, exit code and time, because nobody else sees those two checks. It saves no record of the new tests failing at the base. The saved shape changes with question 8's, under SCHEMA_VERSION 43.
- Question 12, a revert's test deletions. A revert that changes only files its merge commit changed may lose any base test. Foreman does not run the check at the merge commit's parent to list the exact tests that commit added. Reverts are rare and review reads the diff. This is what was built.
- Question 13, whether the issue closes after merge. The PR closes its issue with a closing keyword, so the merge closes the issue and the closed-issue recheck reaches a dependent whose prerequisite no Foreman run owns. The code already did this and did not change.
- Question 14, children and Ready. file_children adds Ready to every child except a CI workflow slice and hands each one straight to admission, because intake ignores Foreman's own label updates. This is what was built.
- Question 15, how a question reaches the human and comes back. The step pauses inside itself, so needs_human has no edge. The status comment shows the question with its reply marker, the line foreman answer and the question's ID, and an issue comment under the human's login that starts with that line wakes the run with the answer. This is what was built.
- Question 16, the parent issue after its children are filed. It gets Done and stays open, and nothing updates it when the children merge. GitHub's sub-issue progress bar already shows that. This is what was built.
- Question 17, the revert run's details. Its slice has one drive criterion, that the default branch no longer carries the merge commit's changes and the check passes. Mutate samples nothing and routes mutations_caught. The regression issue holds the failed check's output. This is what was built.
- Question 18, what the issue text is for a child. Review pass (a) on a child issue also gets the parent issue's text, because Foreman wrote the child's own text from the plan. Pass (a) is the one check meant to catch a plan that drifted from what was asked.

## D16. Where do worker shell commands run, and what network does the attempt container have?

Ruled by Fable, the design's author, on 2026-11-24 (T19 rulings Q1 to Q4, asked by tools coordinator seat an for S7, S9, S10 and S18). The rulings drew what item 3 already meant and closed three gaps the drawing left open.

- Q1. The worker CLI stays on the Foreman host with its model credentials. Every shell command a worker runs goes into the attempt container, which replaces the CLI's own host sandbox as the boundary for those commands. A call whose shell cannot be routed into the container fails closed and runs no command on the host (IM13).
- Q2. How an adapter routes its shell into the container is below the drawing. A model whose CLI cannot route its shell there is not qualified for implement.tests, implement.edit or verify.drive, and dispatch moves to the next qualified model. A reviewer without the route still qualifies; its shell commands, the check included, fail closed. No Codex builder or verifier stays on the host. Until the Codex route is on, Claude does the build, the acceptance tests and Verify on every run, so those three jobs use one family and one quota.
- Q3. One network per run, connected only while Foreman runs the contract's setup commands. After setup the container has loopback only, where the app and its related services listen. The contract's `network` field is `setup` by default, and `run` keeps the network for a repository whose app uses remote test services.
- Q4. `test_report` names one or more generated JUnit XML files inside the checkout. They need not be tracked, so the field is no longer under `rules.paths`, and Foreman removes them before each check run. A list covers a check that runs two test commands (#304). The field defines the test ID that the acceptance test proof and the weakened-check comparison use. `verify_skill` stays under `rules.paths`, because it is a tracked file.
- The T17 cold read of PR #345 at 8201f82b found wording gaps. Fable ruled on three of them on 2026-11-24. Ready added to an issue whose run ended cancelled admits a new run that starts at triage. The repository git-ignores the test reports, so the check leaves the tree unchanged, and doctor's full check requires that. IM13 covers a container that stops in the middle of a call. The coordinator worded the other gaps, including that a reviewer without the route keeps qualifying while its shell commands fail closed.

Warp runs Claude Code and Codex inside the task container, and they call their providers directly from it. Foreman keeps the CLI on the host because model credentials never enter the container where repository code runs. Warp's Docker backend gives each task its own container and removes it afterwards, as Foreman does. [Warp security and networking](https://docs.warp.dev/factories/self-hosting/security-and-networking/) · [Warp runners](https://docs.warp.dev/factories/runners/)

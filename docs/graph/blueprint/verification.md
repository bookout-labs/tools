# Verify Foreman's blueprint

## Structure

On each proposed PR head and merge-group candidate, load the target with duplicate-key and schema checks, compile Foreman with inert adapters, and compare the outer graph and each discovered subgraph. Fail on each difference without an exact waiver, any waiver whose difference disappeared, missing references, unclassified production owners, or stale generated views. Check owner paths, signatures, line budgets, typed schemas, registered halt and retry declarations, and loaded skill and prompt selectors. Enforce the route coverage contract in `target.yaml:rules.routing` against the runtime enums and registered routes. Compare deployed prompts byte for byte to their complete target files. Inventory the actual model order and resolve the expected order from the existing model policy at the admitted release. Judge permissible imports and effects through targeted boundary and runtime checks. A topology match alone cannot certify arbitrary Python or dynamic destinations. [Warp definition checks](https://docs.warp.dev/factories/factory-as-code/)

The projection check and its baseline waivers are a separate migration step. Each waiver must bind one exact difference to a closing issue. A new waiver requires target approval. Re-keying a waiver is not a new waiver. When a build closes part of a waiver's difference, the rest keeps its subject, narrowed to the items still open, under its new ID. When a build edits a runtime prompt, its waiver keeps its subject under the ID of the prompt's changed hash. A new waiver means a new subject.

## Judgment

Run all three synthetic fixtures with real configured workers on every release candidate through the existing eval and smoke entry points. Pin fixture revision, runtime, blueprint, worker policies, scorer revision and spend allowance. For each reached stage grade the recorded evidence against a versioned rubric.

| Stage | Judgment to assess |
| --- | --- |
| Triage | Correct repository and route from the admitted issue. |
| Research | Answer resolves the question with sources at the pinned revision. |
| Spec | Candidate fits the issue and repository, states behavior without dictating code, cites every outside assumption, and links dependencies correctly. |
| Implement | Change fits acceptance, passes the accepted tests and the mutation sample, and publishes the checked tree within the assigned branch. The task compliance scorer grades it. |
| Verify | Each criterion's result matches what the capture shows. |
| Review | Each blocking finding has a failing demonstration or a cited file:line, severity fits real risk, and every round sees the full PR. The review quality scorer grades it. |
| Merge | Report matches GitHub's result, production confirmation matches the deployed merge commit, and dependents become eligible at the right time. |

Store evidence and reason alongside each result. Track hard measures separately, including merge without hand fixes, work and raw tokens, known cost, and edit and review rounds. Pin comparison bands and calibrate rubric labels with human audit before gating on score changes. A hard failure or confirmed regression against the last accepted release blocks the candidate. Repeat uncertain comparisons on both releases. Score live runs with the same rubric outside delivery. Retain private evidence in authorized run storage. The field finish line is three real eligible issues merged in a row with zero hand fixes. [Warp Scorers](https://docs.warp.dev/factories/measure-and-improve/scorers/) · [Warp Benchmarks](https://docs.warp.dev/factories/benchmarks/)

## Trust ladder

The owner agreed to this rollout direction on 2026-11-22. Start with the smallest workflow that meets the contract. Observe failures at limited volume and fix their causes in the owning stage. Reuse the existing dry run, evals, release smoke and three-issue batch. Each proposed target revision and each increase in merge authority starts at the first rung. [Notion's book (archived)](https://web.archive.org/web/20261121015523/https://www.notion.com/a-new-shape-for-work)

| Rung | Evidence to advance | Merge authority |
| --- | --- | --- |
| 1. Synthetic benchmark replays | Use scripted and shadow runs to record intended effects with inert adapters. Pass all fixture expectations and compare scores with the last accepted version. | Record the exact head Foreman would arm. No external mutation. |
| 2. Live smoke repositories | Run the real release smoke against synthetic GitHub repos at the exact release commit. Verify checks, publication, merge observation and recovery. | Exercise D2 only in smoke after the App and outside-writer branch protection probe passes. |
| 3. About three real issues | The coordinator admits one batch. Check each scorecard and require three consecutive eligible merges without a hand fix before expanding. | Scope D2 to this batch and only to repos with proven branch protection. Keep merge_held everywhere else. |
| 4. Normal volume | Admit the next batch only after review of the observed results. Continue per-run scoring and watch stage depth, stop cause and cost. | Expand only the proven GitHub policy and authorized repositories. |

Stop promotion on a failure and fix the observed cause. Re-run the earlier rungs for the resulting revision. Limit volume through admission and release controls already in use. Keep open runs on their pinned release.

Use the Ready label webhook to feed the existing intake. Shadow the candidate events in rung 1. In smoke, test an authentic Ready label event, duplicate and stale deliveries, a repository without the App, a personal repository, and Foreman's own label writes. Assert that the Doing, Needs answer, Stopped and Done labels and the status comment reflect the saved run. Apply the same admission limits for the real batch. ## Changes and versions

Fix implementation when the approved blueprint already expresses the right behavior. Propose a blueprint PR when the rule should change for future runs. Cite the triggering run, scorer result, Warp reference or simplification. Show the owning root cause, generated impact, deletion and addition counts, and why any growth is warranted. Require no benchmark regression and a cold read before the human approves the exact PR revision. Use scorer and benchmark evidence to propose fix PRs for observed failures with pstack `correct` (D7). Agents may propose changes using that evidence. The human controls adoption. Protect the target, linked prompts, glossary, check and waivers with CODEOWNERS. [Warp self-improvement](https://docs.warp.dev/factories/measure-and-improve/self-improvement/)

For each changed stage, give three independent readers the glossary, rendered views and linked contracts. Ask twelve questions about admission, ownership, roots, input identity, worker method, outcome, priority, unknown route, gate authority, caps, allowed effects and an adversarial trace. Withhold code and the key. Record exact input revisions, models and answers. Require all twelve correct for each reader, including the two-repository regression. Have a person check diagram legibility at reading size. Rerun the changed stage with fresh readers after a contract fix.

Use GitHub, the CARR record layer and T3 Code for authorized shared context (see the glossary). Git versions the blueprint. Pin its revision, instruction sources and compatible runtime release on admission. Resume the pinned version for open checkpoints. Keep that release available or use an explicitly approved migration that proves continuation identity and effect recovery. [Warp Blueprint revisions](https://docs.warp.dev/factories/blueprints/)
